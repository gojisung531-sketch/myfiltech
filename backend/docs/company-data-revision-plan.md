# 회사자료 개정·재분석 추적 — B6C 구현 범위와 후속 설계

## B6C 구현 (2026-10-26)

실행 입력 스냅샷·입력 비교·판정/초안별 CURRENT/STALE/UNKNOWN과 읽기 전용 API를 구현했다. 새 실행부터 `core.AnalysisRun`에 정식 자료·관련 원본/메타데이터·요구조건·제품 선택·기준일·정책/코드 식별정보와 결과 스냅샷을 보존한다. 초안은 사용한 저장 판정도 추적한다. 시작/저장 경계의 입력·수동 결과 변화는 전체 결과 저장을 거부한다. 기존 결과에 현재 입력을 소급 연결하지 않았으며 실제 판정37·초안4는 UNKNOWN으로 유지한다.

API·프런트 계약, 복구 및 한계는 [analysis-freshness-b6c.md](analysis-freshness-b6c.md)에 있다. 아래는 **B4B/B5A 당시 작성한 전체 개정 시스템의 설계 기록**이다. 아래 항목 전체를 구현한 것은 아니다. 변경 이벤트별 작성자/사유 대장, 원본 바이트 아카이브·복구, 매칭/적합도 결과 자체의 최신성, 프런트 배지/이동, 부분 재분석·새로운 승인 흐름은 후속이다.

## 이전 설계 기록

B4B 후속 설계 요구이며 이번에 모델·마이그레이션·API·작업 실행을 추가하지 않았다. 실제 자료/저장 판정을 변경하지 않았다. B4B 규칙 변경도 기존 결과를 자동 갱신하지 않는다.

B5A에서도 아래 전체 개정·재분석 추적은 **미구현**이다. 저장 정책/활성 프롬프트를 갱신해도 기존 결과에 stale 표시를 자동 추가하지 않는다. 다음 분석의 최신 입력 경로·수동 수정 검증·미구현 영역의 임시 확인 방법은 `BACKEND_PROGRESS.md` B5A에 구체화했다.

## 개정과 분석 입력의 식별

- 정식 Company/Product/TestReport/Certificate/DeliveryRecord의 승인된 변경에 개정 식별자를 부여한다. 한 번의 자료 반영에서 여러 행이 바뀌면 동일한 반영 단위와 작성자·시각·근거·이전 개정 관계를 기록한다. 원본 파일 SHA, 행/필드 개정, 삭제·철회까지 구분할 수 있어야 한다. 단순 updated_at만으로 과거 입력을 재현하지 않는다.
- 분석 실행에는 사용한 회사자료 개정과 해당 행/원본 버전, 공고·첨부/요구사항 개정, 사용자 제품 선택 상태, 기준일/모드를 고정해 기록한다. 코드/규칙 정책 버전·설정 스냅샷 해시·활성 프롬프트 버전/내용 해시도 포함한다. 비밀키는 저장 대상에서 제외한다.
- 실행 중 회사자료가 바뀌면 한 결과 묶음에 두 개정이 섞이지 않아야 한다. 입력 스냅샷/일관된 읽기 또는 개정 재확인 후 완료 거부 중 구현 전략을 정하고, 결과 묶음과 사용 개정의 원자적 연결을 검증한다.
- B4A에서 발견한 파일명/본문 공고번호 불일치는 사람이 근거로 해소하고 별도 이력으로 남겨야 한다. 폴더명으로 번호를 자동 교정하거나 서로 다른 공고의 첨부를 임의 병합하지 않는다.

## 재분석 필요 표시와 결과의 일관성

정식 자료·공고 입력·제품 선택·규칙/정책/설정/프롬프트 개정이 결과의 입력과 달라지면 기존 결과는 **재분석 필요**다. 마지막 계산 시점, 사용 개정, 현재 개정과 변경 이유를 보여 주어야 한다. 이전 판정값을 그대로 두고 현재 회사 값만 옆에 바꾸어 같은 시점의 비교인 것처럼 표시하지 않는다.

기존 결과는 그 당시 입력 스냅샷으로 조회하거나, 현재 값과 명확히 분리해 개정 차이를 표시한다. 판정·비교표·기술 적합도·초안의 개정 일치 여부를 각각 추적하고, 최신 분석 실패/미실행 상태를 이전 결과의 성공 상태와 혼동하지 않는다. 기존 데이터의 사용 개정을 알 수 없으면 ‘최신’으로 소급 지정하지 않고 출처 미상/재확인 필요로 남긴다.

## 재계산할 범위

| 변경 입력 | 재분석 때 확인할 파생 범위 |
|---|---|
| 제품 사양·등급·가용 제품, 공고 품목/요구사항 | 제품 매칭 점수·후보와 선택 적합성, 기술 적합도, 관련 판정·비교·초안 |
| 성적서·인증·실적·납기 자료 | 자격/규격 커버리지와 적합도, 관련 요구 판정, 답변·증거·파생 초안. 제품 성능 근거가 바뀌면 매칭도 포함 |
| 규칙·허용오차·기준일·가중치/프롬프트 정책 | 해당 정책을 사용한 매칭/적합도/판정/초안. 실행 당시 정책과 변경 이유 기록 |
| 수동 제품 선택·판정·초안 | 자동 결과와 별도 소유/개정 유지. 관련 입력 변경 시 재확인 필요 표시 |

처음에는 의존 범위를 명확히 한 보수적 재계산을 택하고, 부분 재계산 최적화는 결과 일관성 검증 뒤에 한다. 매칭→적합도→판정→초안 중 하나만 바뀐 채 전체가 최신이라고 표시해서는 안 된다. 유료 작업의 대상·예상 범위와 실행 권한은 명시적인 사용자 작업으로 다룬다.

## 수동 작업과 검토 대기 보존

- 수동 선택 제품은 자동 1순위 후보가 달라져도 조용히 교체하지 않는다. 이전 선택·변경자·선택 당시 개정·변경 이유를 보존하고 현재 개정에서 재확인을 요구한다.
- 수동 판정/답변/증거와 초안은 자동 결과를 별도 새 개정으로 만든 뒤 사람이 비교·반영할 수 있어야 한다. 기존 keep_modified/이력·자동 판정 복원 계약을 유지하며 예전 자동 결과로 복원해도 최신성이 자동 인정되지는 않는다. 동시 편집 충돌도 감지해야 한다.
- 대기 관리대장 등록·분류는 정식 회사자료 반영과 구분한다. 검토 대기 151행이 존재하거나 조회됐다는 이유로 정식 개정을 만들거나 제품에 연결하지 않는다. 승인된 정식 반영 시점에만 개정·영향 범위를 기록하고 대기 원문/검토 이력과 연결한다.
- 자료 변경은 재분석 필요를 표시할 수 있지만 새로고침/GET이 적재·재매칭·유료 LLM·초안을 자동 실행하면 안 된다. 쓰기 승인/실행 작업과 읽기 전용 조회를 구분한다.

## 다음 구현 전 확인할 최소 계약과 검증

개정 식별자/불변 스냅샷의 저장 범위, 일괄 반영 단위, 의존 결과의 stale 사유, 수동/자동 개정의 병존과 복원, 재계산 범위/권한을 먼저 확정한다. 그다음 합성 자료로 변경 후 stale·동시 변경·실행 실패·재분석 취소·수동 덮어쓰기 방지·GET 무부작용·정책만 변경된 경우를 검사한다. 실제 공고 식별과 핵심 원본 대응은 별도로 확인하며 전체 대기 행의 일괄 검토/자동 승격을 선행조건으로 삼지 않는다.
