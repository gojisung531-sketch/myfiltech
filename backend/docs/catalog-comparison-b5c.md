# 제조사 자료의 후보 비교 — B5C

공고의 품목과 실제 제안 제품이 확정되지 않아도 현재 카탈로그의 기재 사양을 비교한다. 비교 후보를 정식 연결 제품이나 시험 시료로 자동 승격하지 않는다. B5C 실제 입력·회사 값·원응답·대조 기록은 Git 제외 로컬 기록에 보존하며 완료 결과는 `BACKEND_PROGRESS.md`를 참조한다.

## 기존 서비스에서의 처리

- `match_items(..., confirm=False)`는 기존 점수식으로 후보만 저장한다. `BidItem.matched_product`와 기존 수동 선택은 변경하지 않는다. 일반 호출의 기본 동작은 유지한다.
- `EvaluationContext.for_bid`는 최신 정식 자료와 품목별 후보를 다시 읽는다. 검토 대기 관리대장은 정식 성적서 조회에 포함하지 않는다.
- `rules.evaluate`는 먼저 `normalized.interpretation_review`의 미확정 조건을 확인한다. 이 상태는 수치·자격 규칙과 LLM 답변보다 우선한다. 원문으로 확정할 수 없는 부호·단위·대상·적용 조건을 추정해서 채우지 않는다.
- 확정 연결이 없는 제품 요구는 후보별로 기존 규칙을 적용해 `candidate_comparisons`에 보관한다. 후보의 치수 일치·불일치와 공고 최종 판정을 구분한다. 실제 제안 제품이 판정을 좌우하면 공고 항목은 확인 필요다.
- 동일 카트리지 계열이어도 원통/원추 형상을 별도로 비교한다. 미등록 실적·미연결 제품은 미달의 증거가 아니다. 자체 작성 서류라는 사실도 작성·발급·제출 준비 완료를 뜻하지 않는다. 직접 확인된 수치 미달·유효한 충족 규칙은 유지한다.

## 등록 값과 출처

기존 `Product` 필드에는 확인한 모델별 형식·치수·재질·등급을 사용한다. 원본 파일은 `source_document`, 페이지·원문 인용·표 구획은 `extra.manufacturer_source`와 수동 `DocumentMetadata`로 연결한다. 원문을 확인한 필드만 입력하며, 카탈로그 값이라는 수준을 표시한다.

페어 표의 풍량·차압을 개별 카트리지 정격 필드에 넣지 않는다. `extra.manufacturer_claims`에 제조사 제시값의 비교 연산자·단위·대상과 한계를 보관한다. 효율 하한이 요구 하한보다 낮다는 이유만으로 실제 측정 미달로 판단하지 않는다. 다른 문서의 다른 풍량·재질·옵션을 합쳐 가상의 모델을 만들지 않는다. 소개서의 모델 불명 페어 표는 별도 참고 메타데이터로 남기고 카탈로그 모델에 확정 연결하지 않는다.

`product_evidence`는 확인된 제조사 원문 위치를 반환한다. 원문 위치가 없는 기존 요약은 페이지0·빈 인용으로 유지한다. 시험성적서·제출 완료·시험기관 실측으로 확대하지 않는다.

## 한 차례의 실제 실행

B5C는 기존 `evaluate_bid`를 지정 공고에 직접 호출했다. 상시 워커나 재추출·초안·적합도 경로는 사용하지 않았다.

- `rules_first=True`: 규칙으로 처리한 항목은 LLM에 다시 보내지 않고 미처리 항목만 기존 배치 크기로 묶는다. 전역 설정·활성 프롬프트는 바꾸지 않는다.
- `source_scoped=True`: **정식 성적서·인증서·실적이 아직 없는 카탈로그 후보 전용 실행**이다. 다른 정식 자료가 있으면 중단하고 범위를 다시 검토한다. 이 옵션은 모든 정식 근거를 확인 필요로 낮추는 범용 모드가 아니다.
- 이 모드의 LLM 보조 결과는 제공한 회사 참조에 한정한다. 없는 문서·인용·페이지는 공개 근거로 받아들이지 않는다. 직접 근거가 없는 이행·자격 완료 설명이나 추정 부재·수량·위치를 공개 문안에 사용하지 않는다. 원응답은 실제 LLM 로그와 로컬 기록에 보존한다.
- 원문 해석 제한·미확정 후보를 LLM 문안으로 숨기지 않는다. 규칙으로 확인된 직접 충족·실제 수치 미달은 그대로 유지한다. 기존 수동 판정은 `keep_modified=True`로 보존한다.

실제 호출 후 발견한 명확한 규칙/공개 문안 문제는 해당 항목만 로컬 보정하고 이전 자동 스냅샷을 보존했다. 같은 입력의 유료 판정을 반복하지 않았다. 실제 요청의 범위와 보정 항목을 로컬 영수증·대조 기록에서 구분한다.

## 조회와 다음 단계

기존 비교 API 필드는 유지하고 `comparison_candidates`, `interpretation_review`, `comparison_trace`, `rationale`을 추가했다. 미확정 제품은 `product=null`을 유지하면서 `product_spec`/`company_value`에 후보 사양과 한계를 표시한다. 판정 API의 근거 문서 ID로 실제 등록 원문을 연다. 조회는 유료 분석을 실행하지 않는다. API 확인과 브라우저 화면 확인은 별개다.

다음 단계는 직원에게 실제 제안 모델·옵션을 확인하고 해당 범위의 비교를 검토하는 것이다. 원본 성적서·도면은 공고의 특정 시험·제출·설치 요건에 필요한 항목만 병행 확인한다. 151행 전체 검토나 모든 성적서 확보를 전체 비교의 선행조건으로 두지 않는다.

자료 개정 이력·오래된 결과 자동 표시는 아직 구현하지 않았다. 현재 API에서 새 입력은 다시 읽지만 저장 판정은 과거 입력의 스냅샷일 수 있다. 재분석 전 실제 입력 해시/페이지/프롬프트/기준일과 기존 실행 기록을 비교하고 수동 수정 보존을 확인해야 한다. `company-data-revision-plan.md`의 후속 추적 과제를 구현했다고 보지 않는다.
